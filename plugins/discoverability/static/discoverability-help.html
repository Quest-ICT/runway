Discoverability — SEO+ & GEO

This plugin makes your site legible to search engines and AI answer engines. It adds the layer the platform's built-in SEO deliberately leaves out — it never duplicates a tag the kernel already emits (canonical, hreflang, robots, Open Graph and Twitter cards are already produced for free).

What it adds

SurfaceWhat & where
Structured dataschema.org JSON-LD (WebSite / WebPage or Article / Organization / BreadcrumbList) injected into every indexable page's <head>.
Sitemap/sitemap.xml — every published, indexable page with its hreflang alternates. Pages you mark Exclude from search engines (noindex), and pages whose canonical URL points elsewhere, are left out on purpose: a sitemap recommends pages for indexing, so listing one you told robots to skip contradicts itself.
Crawler rules/robots.txt — tells crawlers what they may fetch. Set the AI-crawler policy below to allow or refuse AI/answer engines, and list any paths to keep crawlers away from. Refusing AI crawlers never removes you from ordinary web search: the AI opt-out names the AI agents only (for example Google-Extended, never Googlebot).
GEO · llms.txt/llms.txt — a compact, machine-friendly index of your pages for LLM / answer engines (opt-in). Honest note: this is a community proposal, not a standard. No major engine documents reading it, and Google states explicitly that no AI-specific file is needed to appear in its AI features. It is cheap to publish and harmless; treat it as an optional extra, not as something your visibility depends on.
GEO · answer schemaA SearchAction (site search) and Speakable hints that enrich the structured-data graph for AI extraction (opt-in).

Configure it

Everything below is per site, on this plugin's settings page (the site console's Settings menu, Discoverability (SEO+ & GEO)), and reaches your pages, robots.txt, the sitemap and /llms.txt at once. The page is in the same sections as this help; each field carries a one-line explanation, and the Learn more links land here. Fields that only matter when a switch is on are hidden while it is off (their values are kept).

Who can change them. The settings page, and the Discoverability card on the dashboard, need the permission Manage discoverability (SEO & GEO) (discoverability|settings). No role holds it until it is granted, so out of the box only the site's superadmin and administrators have it. Grant it to a role or a user on the site's Permissions screen.

What it takes from the site itself. The site's name is the WebSite name on every page, the heading of /llms.txt, the name of a local business that gives none, and the homepage product's name when neither a product name nor an organization name is set. The site's address (its base URL, else https:// plus its first host name; for a site with neither, the address the page was requested at) starts every full URL this plugin builds from a path on the site. The site's languages: each page is described in the language it is served in, and /llms.txt lists each page once, in the site's default language (a page that does not exist in it is listed at its own address).

Structured data for search engines

schema.org JSON-LD in every page's <head>: the site (WebSite), the page (WebPage, or Article for blogs and news), its BreadcrumbList, and the Organization that publishes it. It is on by default and is the switch everything structured depends on — the organization, the homepage product, the per-page types and GEO's search action and speakable hints all disappear while it is off. A page marked Exclude from search engines (noindex) gets no structured data at all, and is left out of /llms.txt as well as the sitemap. A preview gets no structured data either.

  • Default page type — what every page is described as unless Per-page types gives it a page type of its own, which then replaces this one on that page. WebPage (the default) or Article. An Article page carries the page title as its headline instead of its name; its author, dates and images come only from an Article, BlogPosting or NewsArticle block in Per-page types. The form offers only these two; in a hand-edited settings file, anything but exactly Article means WebPage.
  • Breadcrumb trail — on by default. Every page except the home page (/), and except a page whose canonical URL points to another site, gets a trail: Home, then the parent a Per-page types breadcrumb names (if any), then the page, named by its title (or by its path when the title is blank). The first step is always the English word Home, whatever the page's language, and links to the site's root. The home page of another language (/es) is not /, so it gets a two-step trail.
  • Organization name / logo / profiles — identify the site as an entity (knowledge-graph signals, shared by search and AI). Leave the name blank to publish no organization. The logo may be a path on the site (/img/logo.png); it is turned into a full URL for you.

Per-page types (content.schema)

A small YAML document keyed by URL path that declares what particular pages are, so search engines can show them (and, for some types, show rich results). Each page also has a line in the page editor's quality panel that says what it is described as and where that comes from, and the box below this form lists any mistake in this field. A mistake never stops the form from saving and never breaks a page: unreadable YAML gives no page a per-page type, and an unknown type is skipped, so check that box after you save. Per-page types need structured data on, and do nothing on a page marked noindex.

How a page is matched

  • A key is a path pattern starting with /: /pricing matches that page, and a * at the end matches every path that starts with what comes before it (/blog/*). It is a plain text prefix: /blog/* does not match /blog itself (give that page its own key), and /blog* also matches /blogroll; /* matches every page. An exact path wins over a prefix; among prefixes the longest wins. Only that one entry applies: an exact entry and a prefix entry are never combined. A * anywhere else is an ordinary character.
  • A page is matched by its own URL path (its canonical URL, so a page whose canonical is overridden is matched by the override). A page whose canonical URL points to another site has no path on this site, so no pattern that starts with / matches it. A page in another language is matched by its own path too: /pricing does not reach /es/pricing, because what an entry says (questions, names, a breadcrumb parent) is written in one language. Give the translated page its own key (/es/pricing, or /es/* for all of them) with the text in its language; a key such as /* matches every language's pages. The page editor tells a translated page when the default language's entry does not reach it.
  • The value is one type block (type: … plus that type's keys) or a list of blocks when one page is several things at once. Types and keys are case-sensitive, spelled exactly as below: faqpage or Price is not recognised.
  • Quote numbers you mean as text (prices, postal codes): price: "22.00". Unquoted, 22.00 becomes 22.0.
  • Any block may add breadcrumb: { name: …, url: … }: the page's breadcrumb trail then shows that parent between Home and the page. It needs both name and url; a path on the site is made a full URL. When several blocks give one, the first complete one is used. A block may hold only a breadcrumb, with no type.

Page types: what the page itself is

These replace the Default page type on the pages they match; a page has one, the first listed.

TypeKeys
Article, BlogPosting, NewsArticle headline (default: the page title) · description (default: the page description) · image (a list of image URLs; a path on the site is made a full URL) · author (a name) · datePublished, dateModified (YYYY-MM-DD; published as written, not checked). A page that knows its own author and dates (a blog entry) uses those instead. A page with neither a title nor a headline gets none of these.
FAQPage faq: a list of { q: question, a: answer }. A pair missing q or a is left out; with no complete pair the page is still an FAQPage, with no questions, and the page editor and the box below the form say so.
CollectionPage items: a list of { name, url }, published as the page's list (an ItemList that is the page's main entity). An item without url is left out; a path on the site is made a full URL. With no item that has a url, no list is published, and the page editor and the box below the form say so.
WebPage, AboutPage, ContactPage, ItemPage, SearchResultsPage none: they only name what the page is. WebPage takes a page back to the plain type on a site whose default is Article. There is no QAPage or ProfilePage: Google requires each to name its main subject, which a type with no keys cannot do. Questions you write on the page are an FAQPage.

Types that add something to the page

TypeKeys
Product name (default: the page title) · description (default: the page description) · image · sku · price (an offer is published only with a price) · currency (default USD) · availability (InStock, OutOfStock, PreOrder, … or a full schema.org URL; a word is put after https://schema.org/, so spell it as schema.org does). The organization, when named, is the brand. With neither a name nor a page title, no product is published.
Service, ProfessionalService name (default: the page title) · description (default: the page description) · serviceType · areaServed (a list) · offers: a list of { name, price, currency, unit }; an offer without price is left out, currency defaults to USD, and with unit (for example month) the price is per that unit. The organization, when named, is the provider. With neither a name nor a page title, no service is published.
LocalBusiness, CafeOrCoffeeShop name (default: the site name) · street · locality · region · postalCode · country · telephone · url · priceRange · latitude, longitude · hours (a list, for example "Mo-Fr 08:00-17:00") · image. Or locations: a list of those, one business per location (the keys beside locations are then not used). url defaults to the page's address. The address is published only with a street or a locality, the map position only with both latitude and longitude. Even a block with nothing but its type publishes a business, named after the site. Only these two type names work.
Person people: a list of { name, jobTitle, image, sameAs } (sameAs: a list of profile URLs). For one person you can put those keys in the block itself, without people. A person without a name is left out. The organization, when named, is where they work.
ItemList items: a list of { name, url }, without changing what the page is. An item without url is left out; a path on the site is made a full URL. With none that has a url, nothing is published, and the box below the form says so.
 
/pricing:                 # one page, two types
  - type: FAQPage
    faq:
      - { q: "Why ranges?", a: "Scope drives cost." }
  - type: Service
    name: "Advisory Sprint"
    offers:
      - { name: "Sprint", price: "18000", currency: USD }
/coffees:                 # a collection page
  type: CollectionPage
  items:
    - { name: "Ethiopia Guji", url: "/coffee-ethiopia-guji" }

  type: Product
  price: "22.00"

  breadcrumb: { name: "Coffees", url: "/coffees" }
/contact:
  type: ContactPage
/team:
  type: Person
  people: [{ name: "Dana Whitlock", jobTitle: "Founder" }]

If a page shows an FAQ (a <details>/<summary> block) that is not declared here, the page editor's quality check points it out.

Sitemap and robots.txt

/sitemap.xml lists every published, indexable page with its language alternates, and /robots.txt announces it. Pages marked Exclude from search engines (noindex), and pages whose canonical URL points elsewhere, are left out on purpose: a sitemap recommends pages for indexing. Paths crawlers should skip become Disallow: lines for every crawler; AI crawlers you allow get the same lines, and AI crawlers you refuse are already kept off the whole site. Write one path per line (or separate them with commas); a / is added in front when you leave it out, and the path is otherwise written as you typed it. Each line is a prefix, as in every robots.txt: /drafts also covers /drafts/old and /drafts-2024, while /drafts/ covers only what is inside it. Crawlers that follow the robots.txt standard (RFC 9309) also read * as any characters and a final $ as the end of the address.

Custom robots.txt replaces the entire generated file — the Sitemap: line and the AI-crawler rules included — with exactly what you type. It is for the rare site that needs rules this page cannot express; if you use it, re-add the Sitemap: line yourself.

AI crawlers

Whether AI companies' crawlers may read the site. Refusing them never removes the site from ordinary web search: the rules name AI agents only (for example Google-Extended, never Googlebot). inherit follows the platform's default, and the settings page shows what that currently is.

Under Advanced you can decide per class of crawler, because the three classes have opposite consequences:

ClassWhat it doesIf you refuse it
TrainingCollects text to train AI models.Costs the site nothing visible.
Answer enginesFetches pages to answer questions (ChatGPT search, Perplexity…). The site stops appearing in those answers.
Person-initiatedA visit someone asked an AI assistant to make. That visit fails.

A class left on inherit follows the site's policy above it.

The crawlers the rules name, by class:

ClassCrawlers
TrainingGPTBot, ClaudeBot, anthropic-ai, Claude-Web, Google-Extended, CCBot, Bytespider, Amazonbot, Applebot-Extended, Meta-ExternalAgent, FacebookBot, cohere-ai, Diffbot, Omgilibot, Timpibot
Answer enginesOAI-SearchBot, Claude-SearchBot, PerplexityBot, YouBot
Person-initiatedChatGPT-User, Claude-User, Perplexity-User

A crawler whose role is unclear is counted as training: that is what a site refusing AI crawlers most likely means. New crawlers appear faster than plugin releases, so the platform operator can add names (Additional AI crawler names: in the app console, open Plugins and press Settings on the Discoverability row; a restart applies it). Each line (or comma-separated entry) is one name, optionally with its class in front: training=NewBot, retrieval=…, user=… (the class may be written in any case). Spaces, colons and = signs are removed from the name. A name already listed, in any case, is ignored, so a built-in crawler cannot be moved to another class. A name without a class follows each site's overall AI policy (or, on a site whose three classes all come out the same, goes with them); so does one with a misspelt class, which is also logged as a warning.

AI answer engines (GEO)

Opt-in extras for AI assistants: /llms.txt (a compact index of the site, headed by your site summary), speakable hints (the CSS selectors of the parts of a page worth reading aloud or quoting) and a SearchAction from the site search URL. The last two are structured data, so they also need structured data on.

Speakable parts: one CSS selector per line (or separate them with commas). Left blank, they are h1 and main, the default.

The site search URL is the address of your results page, as a path or full URL (a value starting with http is used as it is; anything else is a path on this site). Put {query} (or {search_term_string}) where the search words go (/search?q={query}); without either, ?q= is appended, or &q= when the address already has a ?. Blank publishes no search action.

Honest note: llms.txt is a community proposal, not a standard. No major engine documents reading it, and Google states that no AI-specific file is needed to appear in its AI features. It is cheap and harmless; treat it as an optional extra.

Product on the homepage

For a site that presents a software product: a SoftwareApplication on the homepage only (and on the home page of each other language, such as /es), published by the organization. It needs structured data on. A blank name uses the organization's (or the site's), a blank description the homepage's, a blank URL the homepage; a price of 0 means free, and a blank price publishes no offer. A blank operating system means Web and a blank currency USD, the defaults; neither is checked, so write them as schema.org expects (a currency as its three-letter code). The license, product and screenshot URLs are published exactly as you write them: use full URLs (https://…), because a path such as /license stays a path, which search engines do not accept.

Notify search engines of changes (IndexNow)

When a page is published, changed or removed, the site tells the engines that use IndexNow — Bing, Yandex, Seznam, Naver and Yep. Google does not use IndexNow. It needs two switches: the platform operator's (this server then makes outbound requests) and this site's. The settings page tells you when the platform's is off.

The key is any random string of 8 to 128 letters, digits or dashes — the protocol's rule. It is published at /indexnow-key.txt so the engines can check the site is yours. Nothing is sent until a key is set.

IndexNow also needs the site's own address: a site with neither a base URL nor a host name (such as the platform's catch-all default site) never sends anything, and nothing warns about it.

For the platform operator. Besides the switch, this plugin's platform settings (app console, Plugins, Settings on the Discoverability row) hold the endpoint and four limits. The form accepts only the ranges below; a value written by hand in the settings file (external/plugin-settings/discoverability.yml) or in application.yml is not range-checked, so keep to them. A restart applies any change.

SettingDefaultRangeWhat it does
Seconds to gather changes605–3600Changes are collected for this long, then each site's are sent in one submission. Set by hand, a value below 5 counts as 5 and one above 3600 as 3600.
Maximum URLs per submission10001–10000The rest of a batch is not sent (a warning is logged); those pages are still crawled the ordinary way. Set by hand, a value below 1 counts as 1.
Maximum URLs queued per site50001–100000Once a site has this many waiting, further changes are dropped until the next submission (a warning is logged). Set by hand, a value below 1 counts as 1.

Verify it

  • View any public page's source — look for <script type="application/ld+json">.
  • Open /sitemap.xml and /llms.txt (the latter only when GEO is enabled).
  • Open /robots.txt and read it: check the AI-crawler group matches the policy you chose, and that any paths you excluded appear as Disallow: lines under User-agent: * and in every AI group you allow (a refused AI group is a single Disallow: /, which already covers them).
  • Paste a page URL into Google's Rich Results Test to see the structured data recognized.

Editing these settings affects your live site immediately (no restart). Only this site is affected — every site configures its own discoverability. A few things are the platform operator's, apply to every site and change only on a restart: the default AI-crawler policy that inherit follows, the list of extra AI crawler names, and whether IndexNow is allowed at all.
